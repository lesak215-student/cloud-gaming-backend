## 2. Архитектура и управление схемой базы данных

Создание и изменение структуры базы данных выполняется **строго через SQL-миграции Flyway**.
Автоматическое создание или изменение схемы через Hibernate отключено в `application.properties`:
```properties
spring.jpa.hibernate.ddl-auto=validate
spring.jpa.open-in-view=false
spring.flyway.enabled=true
spring.flyway.locations=classpath:db/migration
```

### Версии схемы (Flyway):
1. **`V1__create_tables.sql`** — создание базовых таблиц:
   - `users`: идентификатор (`BIGINT GENERATED BY DEFAULT AS IDENTITY`), имя, уникальный email (`UNIQUE`), тариф подписки (`subscription_tier`).
   - `games`: идентификатор, уникальное название (`UNIQUE`), жанр, требуемый тариф (`required_tier`), количество доступных слотов (`max_slots`).
   - `gaming_sessions`: идентификатор, внешние ключи `user_id REFERENCES users(id)` и `game_id REFERENCES games(id)`, временные метки начала и завершения, разрешение стрима, статус сессии.
2. **`V2__add_notes_to_gaming_sessions.sql`** — содержательная эволюция схемы:
   - Добавление колонки заметок и служебных причин: `ALTER TABLE gaming_sessions ADD COLUMN notes TEXT;`.
   - Существующие сессии сохраняют все данные в полном объёме (`notes` по умолчанию `NULL`).

## 3. Выполнение требований лабораторной работы

### 1. Персистентность данных
Все данные хранятся в реляционной СУБД PostgreSQL 18. После перезапуска приложения данные остаются на месте, а схема валидируется Hibernate на соответствие JPA-сущностям.

### 2. Связи между ресурсами и целостность
* Сущность `GamingSession` связана с `User` и `Game` связями многих к одному: `@ManyToOne(fetch = FetchType.LAZY)`.
* На уровне базы данных ограничения внешнего ключа (`FOREIGN KEY REFERENCES`) исключают возможность создания сессий с несуществующими пользователями или играми.
* Удаление сущности защищено бизнес-правилами: нельзя удалить пользователя или игру, если у них есть активные или приостановленные сессии (возвращается `409 Conflict`).
* При удалении пользователя или игры с завершёнными сессиями связанные записи безопасно каскадно очищаются, предотвращая нарушение целостности данных.

### 3. Атомарная транзакция над связанными объектами и откат (Rollback)
* Реализована операция перевода игры на техническое обслуживание: `POST /games/{id}/maintenance`.
* Защита от конкурентных запросов: взятие пессимистической блокировки (`@Lock(LockModeType.PESSIMISTIC_WRITE)`) на изменяемые записи гарантирует потокобезопасность проверки лимитов и изменения слотов.
* В рамках единой транзакции (`@Transactional`):
  1. Обновляется количество слотов игры `Game.maxSlots` (например, выставляется `0` для полного ТО).
  2. Все активные и приостановленные сессии этой игры переводятся в статус `COMPLETED`, фиксируется время окончания `endedAt`, а в поле `notes` записывается причина обслуживания.
* При возникновении ошибки на любом шаге (сбой базы данных, нарушение ограничений целостности) транзакция полностью откатывается (**Rollback**): ни слоты игры, ни статусы/заметки сессий не сохраняются. Поведение подтверждено интеграционным тестом `shouldRollbackAllChangesWhenErrorOccursInTransaction` с симуляцией сбоя репозитория.

### 4. Эволюция схемы базы данных
* В проекте представлены две последовательные миграции Flyway (`V1` и `V2`).
* Новая установка автоматически создает полную актуальную схему, а повторный запуск существующей базы сохраняет накопленные данные.

### 5. Решение проблемы N+1 и предотвращение LazyInitializationException
* Для эффективной выборки списка сессий вместе с полной информацией о пользователях и играх используются запросы с `JOIN FETCH`:
  ```java
  @Query("SELECT s FROM GamingSession s JOIN FETCH s.user JOIN FETCH s.game WHERE ...")
  List<GamingSession> findAll(...);

  @Query("SELECT s FROM GamingSession s JOIN FETCH s.user JOIN FETCH s.game WHERE s.id = :id")
  Optional<GamingSession> findByIdWithDetails(@Param("id") Long id);
  ```
  Это гарантирует отсутствие `LazyInitializationException` при отключенном `spring.jpa.open-in-view=false` как в `/sessions/detailed`, так и в стандартных эндпоинтах `GET /sessions` и `GET /sessions/{id}`.
* В эндпоинте `GET /games?hasSlots=true` фильтрация по слотам перенесена в единый SQL-запрос репозитория через агрегатный подзапрос, исключая N+1 запросов подсчёта активных сессий.
* Отсутствие проблемы N+1 строго подтверждено интеграционным тестом с проверкой счетчика SQL-запросов через Hibernate Statistics (`stats.getPrepareStatementCount() == 1`).

### 6. Тестирование
* **Юнит-тесты бизнес-логики (40 тестов):** выполняются **без запуска Spring-контекста** за ~0.2 секунды благодаря in-memory репозиториям на динамических прокси `Proxy.newProxyInstance(...)`.
* **Интеграционные тесты базы данных (4 теста):** в классе `DatabaseIntegrationTest` с `@SpringBootTest` проверяют персистентность связей, целостность внешних ключей, откат транзакций при сбоях и выборку без проблемы N+1.
* Всего в проекте **44 теста**, все проходят успешно.

## 4. Инструкция по запуску

### Шаг 1. Запуск PostgreSQL 18 в Docker
```bash
docker compose up -d
```
СУБД поднимается на порту `5433` (база `cloud_gaming`, пользователь `cloud_gaming`, пароль `cloud_gaming`).

### Шаг 2. Запуск приложения
```bash
mvn spring-boot:run
```
При старте Flyway автоматически применяет миграции `V1` и `V2`. Сервер доступен по адресу `http://localhost:8080`.

### Шаг 3. Запуск тестов
```bash
mvn test
```
Все 44 теста (40 юнит + 4 интеграционных) проходят успешно.

### Шаг 4. Прогон сценариев через curl-скрипт
```bash
bash requests.sh
```
Скрипт проверяет все положительные и ошибочные сценарии (400, 404, 409), сценарий отката транзакции при обслуживании и получение детального списка сессий без проблемы N+1.
